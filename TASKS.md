# Tasks en attente

## Entité "type de recommandation" custom (Gally) + select sur le cross-selling natif

Contexte : le cross-selling natif Shopware (`product_cross_selling`) n'a pas de "code", juste un `name` texte libre par produit (chaque produit a ses propres groupes indépendants, `product_id` en FK, aucune garantie de cohérence de nommage entre produits). On ne peut donc pas s'appuyer sur ce `name` pour mapper vers un code de recommandation Gally.

Piste retenue (mise de côté pour l'instant) : créer une vraie liste de types de recommandation gérée dans le BO, sur le modèle de "Manufacturer".

Découpage :
1. Nouvelle entité globale `gally_recommender_type` (`code` + `label` traduisible) + migration Doctrine.
2. Écran admin CRUD pour la gérer (liste + détail), via les composants génériques `sw-settings`/`sw-entity-listing`.
3. Migration sur `product_cross_selling` : ajouter une colonne FK nullable vers `gally_recommender_type`.
4. Override du composant admin `sw-product-cross-selling-form` (bloc Twig-like du template) : remplacer l'input "name" par un `sw-entity-single-select` sur la nouvelle entité, pour ce champ précis.
5. Côté plugin storefront : lire ce nouveau champ (`code`) pour interroger le `RecommenderManager` de Gally, au lieu du `name` libre.

Point délicat : le point 4 (override d'un composant admin core) — mécanisme officiellement supporté par Shopware (blocks de template), pas un hack, mais demande de bien identifier les bons blocks à overrider.

Statut : fait (commit `a88aef2`). Réconcilié avec la PR [#21](https://github.com/Elastic-Suite/gally-shopware-connector/pull/21) de Romain Ruaud (contenu très proche, `dd594db` ≈ son commit) : nos commits ajoutés par-dessus la sienne (`feat_recommenders`), PR retargetée sur `main`.

## Valider le format de locale avant sync Gally

Contexte : `CatalogProvider::buildLocalizedCatalog()` fait `str_replace('-', '_', $language->getLocale()->getCode())` mais n'importe rien d'autre : si une langue Shopware a un code de locale incomplet (pas au format `xx_XX`, ex. juste `en`), le code invalide part silencieusement vers Gally. Mirrors gally-sylius-connector#54 (`fix-32-catalogLocaleFormat`), qui ajoute une validation stricte côté Sylius.

Piste retenue : dans `CatalogProvider::buildLocalizedCatalog()` (`plugins/GallyPlugin/src/Indexer/Provider/CatalogProvider.php`), après le `str_replace`, vérifier le résultat avec une regex `^[a-z]{2}_[A-Z]{2}$` et lever une `\InvalidArgumentException` explicite (message pointant vers la config de la langue en cause) si ça ne matche pas, plutôt que de laisser passer.

Statut : fait. PR [#27](https://github.com/Elastic-Suite/gally-shopware-connector/pull/27) (branche `feat-catalog-locale-validation`, base `main`).

## Point d'extension avant construction de la requête de recherche Gally

Contexte : côté indexation, `IndexerFormatProductEvent` (`plugins/GallyPlugin/src/Indexer/Event/IndexerFormatProductEvent.php`) permet déjà à un projet custom de modifier les données produit avant indexation (ex. prix custom). Il n'existe rien d'équivalent côté recherche : aucun event n'est dispatché avant construction de la requête Gally dans `Search/Adapter.php`/`CriteriaBuilder.php`/`ProductSearchBuilder.php`, donc impossible d'injecter un contexte custom (ex. un `priceGroupId` que le connecteur ne peut pas déduire seul). Mirrors gally-sylius-connector#56 (`feat-1391443-custom-pricing`), qui ajoute `SearchRequestContextEvent` côté Sylius pour ce cas précis.

Piste retenue : créer un event du même genre (ex. `SearchRequestContextEvent`, propriétés mutables type `priceGroupId`) dans `Indexer/Event/` ou un nouveau `Search/Event/`, le dispatcher dans `Search/Adapter.php` (ou l'équivalent le plus proche du point de construction de la requête, à identifier précisément) juste avant l'appel au SDK Gally, puis exposer un moyen de répercuter la valeur mutée dans la requête effectivement envoyée.

Statut : fait. PR [#26](https://github.com/Elastic-Suite/gally-shopware-connector/pull/26) (branche `feat-search-request-context-event`, base `main`).
